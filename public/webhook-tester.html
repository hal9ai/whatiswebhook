    § 01 Point a provider at it

    Where to paste the URL

    Every service that sends webhooks has a place to register an endpoint URL. Use test or sandbox mode while you explore.

    1. In the Stripe Dashboard, switch to test mode and open Developers → Webhooks.
    2. Add an endpoint, paste your URL, and pick the events to send, such as payment_intent.succeeded.
    3. Send a test event from the endpoint's page, or trigger one with the Stripe CLI: stripe trigger payment_intent.succeeded.
    4. To check the signature here, copy the endpoint's signing secret (whsec_…) into the Signature tab.
    1. In your repository, open Settings → Webhooks → Add webhook.
    2. Paste your URL as the payload URL and set the content type to application/json.
    3. Type any secret. GitHub uses it to sign each delivery with X-Hub-Signature-256.
    4. Save. GitHub sends a ping event right away, and you'll see it here.
    1. In your app's configuration, add a webhook subscription for a topic such as orders/create, with your URL as the endpoint.
    2. Trigger the topic in a development store, for instance by placing a test order.
    3. Shopify signs the body with your app's client secret in X-Shopify-Hmac-Sha256.
    1. In your Slack app's settings, open Event Subscriptions or Slash Commands, and paste your URL as the request URL.
    2. For Event Subscriptions, Slack first sends a url_verification request with a challenge and expects it echoed back. The tester does that for you, so the URL verifies.
    3. Slash commands arrive as a form (application/x-www-form-urlencoded). The Body tab shows the fields.

    Any HTTP request works: any method, any path under your URL, any body up to 256 KiB. Try it from a terminal:

    Terminal
    curl -X POST "https://whatiswebhook.com/in/<your-id>/orders" \
  -H "Content-Type: application/json" \
  -d '{"event":"order.created","id":42}'

    § 02 What it can't do

    It shows the request. It doesn't run your code.

    A tester answers the first question: what exactly does this provider send? The next one is whether your handler deals with it, and that needs the request to reach your code. There are three ways:

    • Replay it. Copy a captured request from the Replay tab and send it to your laptop with curl.
    • Forward it. A tunnel or a provider CLI gives your laptop a public URL while you develop. See how to test a webhook locally.
    • Deploy it. Once the handler works, it needs a home that is always on, with a URL that never changes. See deploy a webhook receiver.

    § 04 FAQ

    Frequently asked questions

    Who can see the requests sent to my webhook URL?

    Anyone who has the URL. It is long and random, so it can't be guessed, but treat it like a password and don't send production data to it. Requests are kept in memory only, for an hour after the URL was last used, and are never written to disk.

    Does the signing secret leave my browser?

    No. The signature check runs in your browser with the Web Crypto API. The secret you paste is never sent to the server.

    Can the tester run my webhook handler?

    No. It shows you what a provider sends. To run your own code, forward the request to your laptop with a tunnel or a provider CLI, replay a captured request with curl, or deploy your handler to a server with a public URL. All three, compared.

    How long does a webhook URL last?

    An hour after it was last used, and at most 24 hours. It keeps the 50 most recent requests, up to 256 KiB of body each. For a URL that never changes, deploy your own receiver.
