CH. 01 A field guide · from an event to your server

What is a webhook?

It's an app calling you back. Instead of asking a service “anything new?” every few seconds, you give it a URL, and it sends you an HTTP request the moment something happens: a payment, a push, an order. Here's how that works, what one looks like on the wire, and where the URL has to live.

§ 01 The short answer

Webhooks, in one paragraph

Quick answer

A webhook is an HTTP request that a service sends to a URL you choose when an event happens. You register the URL once, for instance https://your.app/webhook in Stripe's dashboard. From then on, every payment, refund or failed charge arrives there as a POST with a JSON body describing it, and your server answers 200 OK.

It's the opposite direction of a normal API call: the service starts the conversation, so your app learns about events right away without asking over and over. That's also why the URL has to be public and always on: the internet has to be able to reach it.

Host: your.app

{
  "id": "evt_1Q8…",
  "object": "event",
  "type": "payment_intent.succeeded",
  "created": 1791973162,
  "data": {
    "object": { "id": "pi_3Q8…", "amount": 2000, "currency": "eur" }
  }

Polling every 10 seconds costs 173 requests for each event you learn about, and many APIs rate-limit long before that.

Polling still has its place: it needs no public URL, and it's how you catch up after downtime. Many apps do both. Webhooks for speed, and an occasional API sweep so a lost delivery never goes unnoticed.

§ 05 Reference

Webhook vs API vs WebSocket vs server-sent events

Four ways for two programs to stay in sync. They differ in who opens the connection, and for how long.

Who starts itConnectionLearns of an eventNeeds a public URLTypical use
API call (polling)Your appOne request, again on a timerAt the next pollNoFetching data, catching up
WebhookThe serviceOne request per eventWithin a second or soYes, yoursServer-to-server events: payments, pushes, orders
WebSocketYour app, then both waysKept openImmediatelyNoChat, live collaboration, games
Server-sent eventsYour app, then the server talksKept open, one wayImmediatelyNoLive feeds and progress in a browser

The webhook is the only one where your side must be reachable. That's what makes it simple for the sender, and it's the part that trips people up when they develop on a laptop. How to test one locally →

§ 06 In the wild

Webhooks you've probably met

Payments

Stripe

payment_intent.succeeded, invoice.paid, customer.subscription.deleted: the source of truth for what happened to the money, even if the customer closed the tab.

Code

GitHub

push, pull_request, issues: how CI servers, chat bots and deploy tools learn that someone pushed code.

Commerce

Shopify

orders/create, products/update: how apps sync stock, print labels or update a spreadsheet when an order comes in.

Chat

Slack

The Events API sends JSON when someone mentions your bot; slash commands arrive as form fields. Slack expects an answer within 3 seconds.

Messaging

Twilio

When someone texts your number, Twilio calls your URL with the message as form fields, and your answer can tell it what to reply.

The other direction

“Incoming webhooks”

Slack and Discord also use the word for a URL they give you: POST to it and a message appears in a channel. Same idea, opposite side.

§ 09 FAQ

Frequently asked questions

What is a webhook in simple terms?

A webhook is a service calling you back. You give it a URL; when something happens, such as a payment or a new order, it sends an HTTP request to that URL describing the event. Your app reacts right away, without asking over and over.

What is the difference between a webhook and an API?

With an API call, your app asks and the service answers. With a webhook, the service starts the request and your app answers. Most services offer both: webhooks tell you that something happened, and the API lets you fetch details or act on it.

Is a webhook a GET or a POST request?

Almost always POST, with a JSON body describing the event. Some services send form-encoded bodies instead, such as Twilio for incoming messages and Slack for slash commands.

Do webhooks need a public URL?

Yes. The provider sends the request from the internet, so the URL has to be reachable from the internet, usually over HTTPS. A localhost URL only works on your own computer; while developing, use a tunnel or the provider's CLI.

How do I know a webhook really came from the provider?

Check its signature. Providers sign each request with a secret only you and they know, usually an HMAC-SHA256 of the raw body sent in a header. Recompute it on your side and reject requests that don't match. How, for each provider.

What happens if my server is down when a webhook is sent?

It depends on the provider. Stripe retries for up to three days in live mode, Shopify 8 times over 4 hours, and Slack up to 3 times. GitHub doesn't retry automatically; you redeliver from its delivery log.
